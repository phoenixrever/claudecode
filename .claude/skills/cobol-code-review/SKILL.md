# COBOL 代码审查

对 COBOL 程序做系统化审查，输出按严重程度分级的问题报告。COBOL 大量运行在银行、保险、政府等核心系统中，一个隐蔽的 bug 可能造成资金错误或生产 abend，因此审查要以"程序会不会在生产中出错"为出发点，而不是仅做风格点评。

## 审查流程

1. **确认审查范围**：单个程序、COPYBOOK、还是一批变更。如果用户只给了变更 diff，聚焦变更影响的段落及其数据流。
2. **建立全局认识**：先通读 IDENTIFICATION、ENVIRONMENT、DATA DIVISION，理解程序用途（批处理/在线）、涉及的文件与 DB2 表、关键数据结构（特别是 COPYBOOK 和 REDEFINES），再进入 PROCEDURE DIVISION。
3. **逐维度检查**：按下面四个维度逐项对照。读代码时重点关注：
   - 每个数值运算的溢出、截断、精度
   - 每条 SQL 的返回码检查与索引使用
   - 每个 PERFORM/GO TO 的控制流与边界
   - 事务边界与文件/DB 更新的一致性
4. **输出报告**：严格使用下面的报告模板。代码片段从原文件原样摘录（保留行号），不虚构不存在的代码。

## 严重程度定义

| 级别 | 定义 | 典型例子 |
|---|---|---|
| **Critical** | 会导致 abend、数据损坏、资金错误、安全漏洞 | 数值溢出未被处理、SQL 返回码未检查导致静默失败、除零、缓冲区溢出 |
| **Major** | 逻辑缺陷、明显性能问题、事务完整性风险 | 游标逐行处理大表、COMMIT 位置不当、日期世纪问题、越界风险 |
| **Minor** | 规范违反、可读性差、潜在小问题 | 命名不规范、魔数、缺失注释、死代码 |

无法确定是否真的出问题时，用"可能导致""可能触发"表述并说明触发条件，不要把推测写成确定事实。

## 检查维度

### 1. 逻辑错误与 Bug

COBOL 的数值处理规则与直觉相悖，是 bug 的重灾区。大型机 COBOL 的 MOVE/运算截断规则是**高位截断**，不是四舍五入也不是低位截断，检查时必须牢记。

- **数值溢出**：COMP/COMP-3 字段的 PIC 位数能否容纳所有可能的运算结果。PIC S9(9) COMP 上限约 21 亿（2,147,483,647），乘法（如金额 × 数量）或累加极易溢出。COMP 溢出是静默回绕，COMP-3 溢出会 abend 或产生错误值。
- **中间结果精度**：COMPUTE 中除法的小数位、乘法中间结果在赋值前是否被截断。例：`COMPUTE A = B * C / D` 中 B*C 的精度由 A 决定，可能提前截断。
- **MOVE 截断**：数值字段间 MOVE 位数不足时大型机截高位（123456 放入 PIC 9(4) 得 3456），要检查目标字段 PIC 是否足够容纳源字段全部可能值。
- **非数值数据**：从外部输入（文件、CICS 终端、MQ）读入的字段直接用于数值运算或比较，若输入含空格/字符会 S0C7 abend。检查 `IF WS-AMT NUMERIC` 之类的防御是否到位。
- **除零**：DIVIDE/COMPUTE 的除数可能为 0 的路径（含间接为 0，如被除字段初值为 0）。
- **下标/索引越界**：OCCURS 的数组访问是否受界保护。SEARCH ALL 失败后继续使用下标、PERFORM VARYING 超出 OCCURS 边界、用下标访问时依赖排序结果。
- **循环边界**：PERFORM VARYING ... BY 步长的首次/末次执行、UNTIL 条件的取值时机（测试前置还是后置）、循环体内修改循环变量。
- **GO TO / GO TO DEPENDING ON**：跳转后的段落是否最终能回到主流程；DEPENDING ON 的 NONE 情况（值超出范围）会**顺序落入下一个语句**，这是隐蔽 bug 高发点。
- **REDEFINES**：同一存储区不同视图之间的写入/读取时序。检查是否存在"以 A 视图写入、以 B 视图读取"导致的数据解释错误。
- **88 条件值**：88 级的字面量与源数据实际编码（含前导零、补位）是否一致，如 `88 MALE VALUE '1'` 而数据实际是 `'01'`。
- **日期处理**：YYMMDD 两字节年与 YYYYMMDD 的比较/运算混用、世纪边界（1900/2000 判定）、跨月日期的加减（如月末 + 1 天）是否正确。
- **STRING/UNSTRING**：STRING 目标缓冲区长度是否足够（ON OVERFLOW 是否处理）、UNSTRING 的 DELIMITED BY 边界与 POINTER 语义。
- **未初始化数据**：WORKING-STORAGE 初值依赖（VALUE 子句），特别是 VARYING 依赖上一轮执行残留的字段（批处理程序重入时）。
- **文件 EOF 处理**：AT END 之后的继续处理路径，EOF 后再次 READ 的错误。
- **SIGN 与 COMP-3 符号位**：外部数值的符号 nibble（F 正 / D 负）约定与转换是否正确。
- **COPYBOOK 版本一致性**：调用的 COPY 成员与实际表/文件布局（字段长度、新增列）是否匹配。

### 2. 性能问题

批处理程序跑几小时和跑几分钟的差别，通常不在语言本身而在 SQL 和循环结构。

- **游标逐行处理代替集合操作**：`DECLARE CURSOR` + 循环 `FETCH` + 每行 UPDATE/DELETE 的模式，几乎总能用一条带 WHERE 的集合 SQL 代替。看到游标先问"能不能写成一条 SQL"。
- **循环内执行 SQL**：PERFORM 循环体内有 EXEC SQL，行数大时是灾难。检查能否合并为批量操作或多行处理。
- **全表扫描**：SELECT 的 WHERE 列是否有索引、`LIKE '%xxx'` 前导通配符（无法用索引）、对索引列做函数运算（`WHERE CHAR(DATE_COL) = '...'`）导致索引失效。
- **OR 条件**：`WHERE A = x OR B = y` 常导致优化器放弃索引，考虑拆成两条 SQL 或用 UNION。
- **不必要的 SORT**：SORT 只为后续顺序处理，而输入文件本身有序或可用索引替代。
- **重复 OPEN/CLOSE**：循环内反复 OPEN/CLOSE 文件或频繁连接，应提到循环外。
- **每行 COMMIT**：批处理中逐行 COMMIT 会产生大量日志 I/O 与锁开销；COMMIT 频率要按恢复需求权衡（一般按批次，如每 1000 行）。
- **顺序搜索大表**：对 OCCURS 大数组用顺序遍历查找（PERFORM VARYING + IF），应改为 `SEARCH ALL`（二分）或索引文件直读。
- **FETCH 未限制行数**：FETCH 循环无行数上限保护，数据异常时程序长时间运行。
- **不必要的中间文件**：写入临时文件再读回做处理，常可合并为单遍处理。

### 3. 编码规范

规范检查的目的不是审美，而是降低维护成本——COBOL 程序常被维护几十年，代码的每个模糊处都是未来生产事故的种子。只报告有明显负面影响的规范问题，不做吹毛求疵。

- **固定格式布局**：列位置合规——1-6 序号区、第 7 列指示符（`*` 注释、`-` 续行）、8-11 列 A 区（DIVISION/SECTION/段落名/01/77）、12-72 列 B 区、73-80 标识区不得出现代码。
- **结构顺序**：DIVISION/SECTION 按标准顺序排列；DATA DIVISION 中 FILE SECTION / WORKING-STORAGE / LINKAGE SECTION 的条目层级（01/05/10...）递进合理。
- **命名**：数据名体现含义（避免 WS-TEMP1、WS-FLAG2 这类），段落名通常动词开头且能表达动作（如 `2000-VALIDATE-INPUT`），88 条件名表达状态。
- **缩进与块结构**：IF/ELSE/END-IF、PERFORM/END-PERFORM、EVALUATE 的缩进一致；`IF` 与 `ELSE` 配对清晰，避免连续 IF 无 ELSE 造成的悬挂歧义。
- **段落职责**：一个段落完成一件明确的事；段落体过长（如超过数百行）通常意味着职责混杂。
- **魔数**：业务代码中散落的字面量（利率、状态码、限额）应定义为 88 或独立常量字段，便于集中修改。
- **死代码**：未被调用的段落、已注释掉的大块旧代码（若确认为历史遗留，标注为 Minor 建议清理）。
- **注释质量**：注释解释"为什么"（业务规则、异常处理的理由），而不是复述代码本身。
- **EVALUATE vs 嵌套 IF**：多重互斥条件用 EVALUATE 更清晰；多个独立条件嵌套 IF 判断逻辑优先级是否正确。

### 4. 安全与数据完整性

核心系统的数据完整性优先于一切，宁可让程序失败（可重跑）也不静默产生错误数据。

- **SQLCODE 未检查**：INSERT/UPDATE/DELETE 后未检查 SQLCODE（含 SQLWARN、+100 之外的处理）。DB2 的 `-911`（死锁/超时）、`-904`（资源不可用）等若不处理，程序会继续执行，产生数据不一致。检查是否有 WHENEVER 或逐条判断。
- **事务边界**：COMMIT/ROLLBACK 的位置与频率——若文件更新与 DB 更新交织，程序中途失败时两者不一致（文件已写、DB 未提交）。检查恢复/重跑逻辑是否覆盖。
- **动态 SQL 注入**：字符串拼接构造 SQL 且输入来自外部（终端、文件、接口），存在注入风险；应使用参数化（宿主变量）。
- **输入校验**：外部输入未经校验直接进入数值运算、SQL 谓词或作为数组下标。重点检查金额、日期、账号字段的格式与范围校验。
- **敏感数据暴露**：账号、证件号等敏感信息被写入日志、中间文件、SYSOUT 或 DISPLAY 输出，未脱敏。
- **权限检查**：在线程序（CICS）中，交易入口未验证用户权限或终端授权。
- **并发与锁**：多个程序并发更新同一文件/表时的锁策略；OPEN EXTEND 并发写同一文件的追加冲突。
- **空值处理**：DB2 NULL 进入宿主变量后（INDICATOR 变量未检查）参与运算或比较，结果意外。COBOL 宿主变量不会自动感知 NULL，必须检查 INDICATOR。
- **审计追踪**：资金类变更（金额修改、账户状态变更）是否留有审计记录或更新日志。

## 报告模板

输出严格使用以下结构（标题层级、字段顺序保持）。报告语言用中文，代码片段、字段名、段落名保留原文。

```markdown
# COBOL 代码审查报告

## 程序概要

| 项目 | 内容 |
|---|---|
| 程序名 | `<PROGRAM-ID>` |
| 类型 | 批处理 / 在线（CICS/IMS） |
| 审查范围 | 完整程序 / 变更段落 / 指定 COPYBOOK |
| 代码行数 | `<数字>` |

## 问题统计

| 严重程度 | 数量 |
|---|---|
| Critical | n |
| Major | n |
| Minor | n |

## 审查结论

一段话总结：程序整体质量判断、最需要优先处理的风险点、是否建议进入生产前的整改。

## Critical

### [C1] `<问题标题>`

- **位置**：`<段落名>`（约第 n 行）
- **代码**：
  ```cobol
  <原样摘录的代码片段>
  ```
- **问题**：说明为什么这是问题、在什么输入/条件下触发、后果是什么（abend / 数据错误 / 资金风险）。
- **建议**：给出具体修复方向，必要时给出修改后的代码示例。

（每个 Critical 重复以上结构；没有则写"无"）

## Major

（同上结构，编号 [M1]、[M2]...；没有则写"无"）

## Minor

（同上结构，编号 [m1]、[m2]...；没有则写"无"）

## 修复优先级建议

按修复顺序列出建议，例如：
1. [C1]（阻断上线，修复后需回归测试）
2. [M2]（影响批处理窗口，建议本迭代修复）
3. ...
```

补充要求：
- 每个问题必须落到具体位置（段落名或行号），引用真实代码片段。**不要虚构代码**——若不能确定代码原貌，引用时保持原样。
- 没有把握的推测性发现放入 Minor 或直接不报，避免噪音淹没真正的问题。
- 如果用户提供了多个程序或对比了变更前后版本，报告中按程序分节，最后给出跨程序的共同问题。
